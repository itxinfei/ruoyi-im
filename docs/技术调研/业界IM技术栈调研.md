## 一、结论先行

调研了 **6 个商业 IM 产品** + **10 个开源 IM 项目**后，有三条结论对本项目最有价值：

1. **没有"标准 IM 技术栈"，但有"标准 IM 分层"。** 无论用 Go / Java / Erlang / Python，成熟 IM 的分层几乎一致：**接入层（长连接）→ 路由层（连接定位）→ 消息总线（MQ）→ 状态层（Redis）→ 存储层（消息库 + 关系库 + 检索）→ 推送层**。技术选型可以变，这六层不能少。
2. **消息存储几乎没人用 MySQL 单库扛全量。** 高规模项目一致转向 **宽列存储（Cassandra / ScyllaDB）** 或 MongoDB。MySQL 的定位是"用户/权限/关系等元数据"，不是"消息流水"。
3. **选型的第一驱动是团队能力，不是性能排名。** 多个来源反复强调：Rocket.Chat 适合 Node 团队、Mattermost 适合 Go 团队、Matrix 适合有协议治理能力的团队。本项目沿用 Java 生态，本身就是合理的团队能力驱动决策。

**对本项目最关键的一条**：本项目定位是**企业内网私有化、钉钉式协同**（日活规模有限、强合规、强协同），不是**亿级 C 端社交**。因此业界那些"为海量规模做的取舍"（Cassandra/ScyllaDB、Kafka 全量消息流水、Erlang 长连接）**大部分不应照搬**。真正值得吸收的是**分层结构与消息可靠性机制**（序号/游标/幂等/回执），而非具体的重型组件。

### 3.2 关键观察

1. **Go 是当前开源 IM 的主流语言**（OpenIM、Mattermost、Tinode、Lumen、KamaChat 均为 Go）。原因：并发模型天然适合海量长连接，单服务内存占用低。
2. **Java 系仍有稳固位置**（WildfireChat、MobileIMSDK、Openfire）。优势是**国内政企生态、信创适配、Java 人才储备**——这恰好与本项目的定位一致。
3. **没有项目用单一数据库扛全部负载**，最少也是"关系库 + 缓存"两层。
4. **消息队列几乎是标配**（OpenIM 用 Kafka、Zulip 用队列、Discord 用 Kafka 做 CDC 与扇出）——用于解耦写入与投递、削峰。

## 四、业界共识：IM 分层技术栈

多个来源（Stream 官方博客、系统设计分析、大厂架构复盘）给出的分层高度一致：

| 层 | 职责 | 业界主流选型 | 本项目对应 |
|----|------|------------|-----------|
| **接入层** | 长连接维持、鉴权、连接数分流 | Go（gorilla/websocket、gws）；Java（**Netty**、t-io、Spring WebSocket）；Node（ws、socket.io、uWebSockets.js） | Spring Boot WebSocket |
| **路由层** | 按用户/群 ID 定位连接实例 | Redis 存 "用户 → 网关实例" 映射；一致性哈希 | Redis 在线状态 |
| **消息总线** | 解耦写入与投递、削峰、扇出 | **Kafka / RocketMQ / Redis PubSub**；瞬态事件（typing/presence）走 Redis Pub/Sub，消息走 Kafka | ⚠️ 当前定版**未设 MQ** |
| **状态层** | 在线状态、未读数、last-read、typing | **Redis**（不需持久化、高频读写） | Redis |
| **存储层** | 消息流水 / 元数据 / 检索 / 附件 | 宽列库（Cassandra/ScyllaDB）存消息 + 关系库（MySQL/PG）存元数据 + **ES/OpenSearch** 检索 + **对象存储**存附件 | MySQL 8（全量）+ Redis 7 |
| **推送层** | 离线推送 | APNs / FCM / 厂商推送 / Web Push | 内网场景可弱化 |
| **客户端层** | 多端交付 | Web 用 React/Vue；桌面 **Electron**（主流）或 Tauri（轻量新选）；移动 Flutter/RN/原生 | Vue 3 + TS（Web） |

### 4.1 消息存储的行业共识（最重要的一条）

Stream 的官方分析与 Discord 的演进史给出同一个结论：**没有任何单一数据库能覆盖 IM 的全部负载**，因为负载是"跛脚的"：

| 数据类型 | 推荐存储 | 原因 |
|---------|---------|------|
| **消息、reaction、编辑** | 宽列库（Cassandra / ScyllaDB） | 追加写为主；按 `channel_id` 分区 + Snowflake ID 聚簇 → "取最近 N 条" = 一次 seek + 顺序读 |
| **用户/频道/成员/权限** | 关系库（PostgreSQL / MySQL） | 量小、多表 join、需要事务 |
| **在线状态/未读/typing** | Redis | 高频变动、无需持久化 |
| **全文检索** | Elasticsearch / OpenSearch | 只有倒排索引能让 `LIKE '%term%'` 变快 |
| **附件/图片/音视频** | 对象存储（S3 / MinIO / OSS） | 便宜、CDN 友好，避免 blob 入库 |

**Discord 三次迁移的教训（值得本项目记住）：**

| 时期 | 存储 | 为什么换了 |
|------|------|-----------|
| 2015 | MongoDB 单副本 | ~1 亿条消息时工作集超出 RAM，读开始落盘；文档级锁导致 p99 不可控 |
| 2017–2022 | Cassandra（12 → 177 节点） | 数据模型对了，但 **JVM GC 停顿**导致 p99 尖刺；compaction 风暴抢占 IO；大频道热分区 |
| 2022 → | **ScyllaDB**（C++ 重写，无 GC） | 节点 177 → **72**；p99 读 40–125ms → **~15ms**；p99 写 5–70ms → **~5ms** |

> 核心教训：**"MongoDB 失败不是 MongoDB 的错，是负载与模型不匹配"**。选型的本质是让**存储引擎的访问模式**匹配**业务的读写模式**。

### 4.2 消息可靠性机制（与规模无关的通用共识）

这些不依赖规模，**任何 IM 都应实现**，是本项目最该吸收的部分：

| 机制 | 说明 |
|------|------|
| **服务端分配序号（Snowflake / Sequence ID）** | 客户端**按序号排序，不按时间戳排序**——分布式下时钟偏移会导致因果倒置 |
| **游标分页** | `给我 > last_id 的消息` 是主键范围扫描，避免 OFFSET 深翻页 |
| **缺口检测（Gap Detection）** | 收到 ID 5 又收到 7 → 明确知道 6 缺失，主动补拉 |
| **幂等 + 去重** | 客户端以本地 `last_read_id` 为准，服务端按 `message_id` 去重，避免重复投递可见 |
| **至少一次投递 + 应用层 ACK** | TCP 的"发送成功"只意味着进了内核缓冲区，不代表对端收到；**必须在应用层做 ACK** |
| **抖动重连（Jittered Reconnect）** | 2021 Slack 故障后成为行业标准：重连加随机抖动，避免重连风暴打垮路由层 |
| **读扩散 vs 写扩散** | 群聊普遍用**读扩散**（inbox-pull）；纯写扩散会让存储放大 50–500 倍 |

## 五、本项目定版 vs 业界：逐项对照

本项目定版：JDK 25 + Spring Boot 4.1.1 + MyBatis Plus + Spring Security + JWT / Vue 3 + TS + Vite + Element Plus + Vuex 4 / MySQL 8 + Redis 7 + 原生 WebSocket。

| 维度 | 本项目定版 | 业界主流 | 评估 |
|------|-----------|---------|------|
| **后端语言** | Java（JDK 25） | Go 居多（开源）；Java 在政企/信创稳固 | ✅ **合理**。内网私有化 + 若依生态 + 团队 Java 背景，Java 是团队能力驱动的正确选择。Go 的性能优势在"十万级并发连接"才显现，本项目规模用不上 |
| **长连接** | 原生 WebSocket（JSON 帧） | Netty / gorilla / 原生 WS | ✅ 合理，⚠️ **建议**：若并发连接数增长，Spring 原生 WS 在万级连接时的线程模型会成为瓶颈，应预留 Netty 接入层的位置 |
| **消息存储** | MySQL 8 单库 | 宽列库（Cassandra/ScyllaDB）+ 关系库分离 | ⚠️ **主要风险点**。见 5.1 |
| **消息队列** | 无 | Kafka / RocketMQ / Redis PubSub | ⚠️ **建议补齐**，见 5.2 |
| **缓存/状态** | Redis 7 | Redis | ✅ 一致 |
| **检索** | 未明确 | ES / OpenSearch | ⚠️ 建议明确，见 5.3 |
| **对象存储** | 未明确（原代码本地 commons-fileupload） | S3 / MinIO / OSS | ⚠️ 建议明确，见 5.3 |
| **前端** | Vue 3 + TS + Vite | React/Vue 均可；TS 已是默认 | ✅ 合理 |
| **桌面端** | 未明确（当前为 Web） | **Electron 为主流**（钉钉/微信PC/Slack/Discord 均用），Tauri 为轻量新选 | ⚠️ 若要做桌面端，见 5.4 |
| **部署** | Docker + Nginx | Docker/K8s + 反向代理 | ✅ 合理 |

### 5.1 MySQL 存全量消息：风险与建议

**风险**：MySQL 的 B+Tree 在**大表持续追加写 + 按会话时间序分页**这个组合下表现不佳，业界普遍反馈"分库分表复杂"。

**但本项目大概率不需要 Cassandra**，理由是规模：

| 规模档位 | 建议 |
|---------|------|
| 日消息 < 10 万、单会话历史 < 百万条 | **MySQL 完全可以**。做好分区表（按月/按会话哈希）+ 覆盖索引即可 |
| 日消息 10 万–1000 万 | MySQL 分库分表，或引入 MongoDB 存消息流水 |
| 日消息 > 1000 万、大群/万人群 | 才需要 Cassandra / ScyllaDB |

**本项目建议（分级，不推翻定版）：**
1. **表设计层**：消息表按 `conversation_id` 分区或按月分区；主键用**雪花 ID**（时间有序），建立 `(conversation_id, msg_id)` 联合索引 → 让"取最近 N 条"走索引范围扫描而非排序
2. **保留演进路径**：在架构文档中写明"消息存储层可替换"，DAO 层不要泄漏 MySQL 方言
3. **不引入 Cassandra**，除非业务明确要求万人群 + 亿级消息

### 5.2 消息队列：建议补齐

业界共识：**瞬态事件（typing / presence / 在线状态）走 Redis Pub/Sub；消息本身走 Kafka（持久化、可重放）**。

本项目是单体 Spring Boot，引入 Kafka 属重型。建议**分级**：

- **阶段一（当前）**：用 **Redis Pub/Sub** 或 Spring Event 做多实例间的消息扇出，先解决"多副本部署时消息投递到正确的连接实例"这一刚需
- **阶段二**：若出现削峰需求（批量审批通知、全员广播），再引入 RocketMQ / Kafka

**关键**：这一层不能省——**只要后端有多于 1 个实例，就必须有跨实例的消息路由机制**，否则用户 A 连在实例 1、用户 B 连在实例 2，消息就投不到。

### 5.3 检索与对象存储：建议明确写入定版

| 组件 | 建议 | 理由 |
|------|------|------|
| **全文检索** | 消息/文件搜索用 **Elasticsearch** 或 **OpenSearch**；内网轻量化可用 **MySQL 全文索引 + 分词** 起步 | 业界唯一能让 `LIKE '%term%'` 快的方案是倒排索引；但内网小规模可先降级 |
| **对象存储** | **MinIO**（可私有化、S3 兼容、单机可跑） | 与"内网私有化"定位最契合；避免 blob 入库拖垮数据库 |

### 5.4 桌面端：Electron vs Tauri

若本项目要做 PC 桌面端（钉钉式体验的关键）：

| 框架 | 体积 | 内存(空闲) | 启动 | 生态 | 适用 |
|------|------|-----------|------|------|------|
| **Electron** | ~40MB+ | ~150MB | 中 | **大而成熟** | 钉钉/微信PC/Slack/Discord/VSCode 均用；复杂 UI + 深度 OS 集成 + 快速迭代 |
| **Tauri** | ~3MB | ~50MB | 快 | 成长中 | Rust 后端 + 系统 WebView；体积小、安全、资源占用低 |
| **Flutter** | ~10MB | ~70MB | 快 | 成长中 | 自绘 UI，多端一致，需学 Dart |

**建议**：**Electron**。理由——国内企业 IM（含钉钉、喧喧）普遍选 Electron，且**信创场景对国产 Linux（麒麟/Deepin）的支持 Electron 最稳**；Tauri 依赖系统 WebView，在国产化系统上兼容性风险更高。

## 六、值得吸收的 8 条工程实践（与规模无关）

这些来自 Discord/WhatsApp/Slack 的公开教训，**不增加架构复杂度但显著提升质量**，建议直接写入本项目的 `06-WebSocket 实时协议.md` 与 `04-数据模型与数据库设计.md`：

1. **服务端分配消息序号，客户端按序号排序**（不按客户端时间戳）——避免时钟偏移导致因果倒置
2. **游标分页而非 OFFSET 分页**——`WHERE conversation_id=? AND msg_id > ?`
3. **缺口检测**——客户端收到非连续序号时主动补拉，而非静默丢消息
4. **应用层 ACK + 至少一次投递**——TCP 成功 ≠ 对端收到
5. **抖动重连（Jittered Reconnect）**——重连间隔加随机抖动，避免重连风暴（Slack 2021 故障的直接教训）
6. **消息幂等**：按 `message_id` 去重，客户端以本地 `last_read_id` 为准
7. **群聊读扩散**——不按成员数写扩散，避免存储放大 50–500 倍
8. **已读回执批量上报**——高频群聊下，逐条回执会反噬主消息通道，应定时批量压缩上报
