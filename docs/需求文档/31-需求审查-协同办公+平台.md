## A: 模糊（Ambiguous）

### A1. [PL-A] 审批模板生命周期状态机完全缺失

**位置**：`09` 八. PL-A-007
**问题描述**：
API 06 定义了 `POST /im/approval/templates`（创建）、`PUT /im/approval/templates/{id}`（更新）、`POST /im/approval/templates/{id}/publish`（发布）、`DELETE /im/approval/templates/{id}`（停用），隐含了 **草稿→发布→启用→停用→删除** 的状态链。
但 `09` 审批需求中**完全没有定义模板的状态枚举**，没有说明：
- "草稿"状态下是否可以编辑？
- "发布"后是否可回退为草稿？
- "停用"是否等于"删除"？物理删除还是逻辑删除？

**影响**：开发者需自行猜测模板状态机，极大可能与实际业务逻辑偏离。

---

### A2. [PL-A] "待审批" 与 "审批中" 混为一谈

**位置**：`09` 8.2 审批状态表 vs `04` im_approval 表 status 字段
**问题描述**：
需求文档定义审批状态 4 种：PENDING / APPROVED / REJECTED / CANCELLED，将"待审批"与"审批中"合并为 PENDING。
数据库 im_approval.status 区分了 **5 种**：
```
1=待审批  2=审批中  3=已通过  4=已驳回  5=已撤回
```
"审批中"（部分节点已审批通过、流程继续）与"待审批"（尚未开始或初始等待）合并为同一个 PENDING，前端无法区分"尚未开始审批"与"已审批部分节点"两种不同场景。

**影响**：审批追踪页面（PL-A-004）需要一个进度条来显示"当前审批节点"，如果只有 PENDING 状态，前端无法判断当前进度。

### A3. [PL-A] 转交行为完全未定义

**位置**：`09` 八. 审批需求 vs `06` API 6.2 `PUT /im/approval/{approvalId}/transfer`
**问题描述**：
API 已提供转交端点，但需求文档**没有任何关于转交的描述**，包括：
- 谁可以转交？仅限当前审批发起人，还是当前节点审批人？
- 转交时选择的审批人范围：同部门？任何人？
- 转交后原审批人意见是否保留显示？
- 被转交人拒绝/通过后，原审批人是否可见？
- 是否有转交次数限制？避免无限循环转交。
- 转交是否需要填写转交原因？

**影响**：转交是高风险操作（涉及权限委托），完全缺失会导致实现不一致。

## C: 约束缺失（Missing Constraint）

### C1. [CO-F] 群文件删除权限：上传者自己能否删除自己的文件？

**位置**：`09` CO-F-005 "文件删除：群主/管理员可删除任意文件"
**现状**：明确只写了"群主/管理员可删除任意文件"，但未说明**普通成员能否删除自己上传的文件**。
**歧义**：
- 若不可删除：用户上传错文件无法自助撤销，体验差。
- 若可删除：需明确仅自己上传的 or 任意文件。
- 需统一规则。

**修复建议**："群主/管理员可删除任意文件；文件上传者可删除自己上传的文件（需二次确认）"
