## 零、先回答最纠结的问题

### Q：UniApp 到底能不能做桌面端？

**短答案：不能。竞品无一家用 UniApp 做桌面端；桌面 IM 事实标准是 Electron / CEF，国内更统一收敛到 Electron。**

| 竞品 | 桌面端技术 | L1 导航 | L2 会话/侧栏 | L3 聊天区 |
|------|-----------|---------|-------------|----------|
| 钉钉 | CEF(早期) → Flutter Dutter(新模块) | Flutter/原生 | WebView(HTML) | WebView(HTML) |
| 飞书 | **Electron**(确认) | Web | Web | Web |
| 企业微信 | CEF + WebView2 + Native | Native/Web | Web | Web |
| 微信 PC(参考) | ** Electron**(确认) | — | — | — |
| Slack/Discord | **Electron** | — | — | — |

三家竞品的 L2 / L3 底层全部是 **Chromium 渲染 HTML/CSS/JS**。UniApp 桌面端输出本质上是 H5 WebView——用来做 IM 三栏布局等于给自己戴上手铐跳舞。

## 一、前端技术选型三条路线对比

> **本节是决策重点。** 你必须选一条路，后续所有前端开发围绕此展开。

### Route A：Vue 3 + Electron（推荐 ✅）

```
桌面端：Vue 3 + Vite + Element Plus → Electron 壳 → 安装包 ~100MB
移动端：暂不做 / 后期单独项目
覆盖：Windows / macOS / Linux(含信创)
复用度：现有代码 100% 复用
```

| 维度 | 评估 |
|------|------|
| 代码改动 | 极少——新增 `electron/` 主进程目录 + `electron-builder` 配置 |
| 三栏布局 | 已在手，套 Electron 后无需重构 |
| Design Token | 已在手 |
| WebSocket 协议 | 不动 |
| 桌面能力（全局托盘/通知/全局快捷键/离线存储） | Electron 全部原生支持 |
| 竞品对齐 | 飞书 / 微信 PC / Slack / Discord 同路径 |
| 信创兼容 | Electron 内置 Chromium，不依赖系统 WebView → **麒麟 / Deepin 兼容最稳** |
| 包体积 | ~100MB（Vite 打出来的资源 ~20MB + Chromium ~80MB）|
| 开发体验 | `npm run dev` 浏览器热更新，`electron:build` 出安装包 → 与当前工作流无缝衔接 |
| 劣势 | 不覆盖移动端；包体积偏大（但已是企业 IM 常态）|

**总评**：继续沿用现有代码堆，仅加一个"外壳"。投入最小，风险最低，与竞品一致。

### Route B：uni-app 全端（不推荐 ❌）

```
所有端：uni-app (Vue 语法子集)
桌面端：uni-app H5 + Electron 壳（别扭）
覆盖：H5 / 小程序 / App / 桌面壳
代码改动：几乎重写所有组件
```

| 维度 | 评估 |
|------|------|
| 三栏布局 | uni-app 桌面端渲染走 H5 模式，三栏在 1366px+ 屏幕上体验差 |
| Element Plus | **完全不可用**，需替换为 uView / ThorUI |
| Design Token rpx 适配 | 已有 Token 体系与 rpx 单位摩擦极大 |
| 消息性能 | 桌面端长列表虚拟化 uni-app 实现远不如 Element Plus |
| 桌面体验 | 无法做"最小化到托盘"、"全局快捷键"、"原生通知"等桌面标配 |
| 竞品对齐 | **没有任何一家主流 IM 桌面端用 uni-app** |
| 信创兼容 | uni-app Electron 壳兼容性风险叠加 |

**总评**：你之前提出的"前端改用 uni-app"，经过调研后 **明确不推荐**。UniApp 的甜蜜区是「H5 + 小程序 + 移动 App 一套代码多端」，不是桌面端。桌面端用 uni-app = 反向优化。

### Route C：双栈（桌面 Web + 移动 uni-app 独立项目）

```
桌面端：Vue 3 + Electron（独立工程，复用 Design Token / API 层）
移动端：uni-app（独立工程，仅共用 HTTP/WebSocket API 契约）
```

| 维度 | 评估 |
|------|------|
| 覆盖 | 桌面完整 + 移动端可独立迭代 |
| 工程量 | **两套前端工程**，开发/设计/同步 Token 成本翻倍 |
| 后端 API | 二者共用同一套 RESTful + WebSocket 接口 |
| 适用场景 | 未来确实要做移动 App（考勤打卡 / 外勤签到） |
| 风险 | 双栈同步问题会长期存在 |

**总评**：远期可走，但**一期不建议**。一期先把桌面打穿，二期再开移动栈。

### 🔴 决策卡

| 项 | 现状 | 选项 | 当前推荐 |
|----|------|------|---------|
| 前端框架 | Vue 3 + TS + Vite + Element Plus | A: Electron B: uni-app C: 双栈 | **A** |
| 移动端 | 未规划 | A: 暂不做 B: 二期双栈 | **A** |

> 👉 **请你拍板：是否走 Route A（Vue 3 + Electron，移动端暂不做）？**
>
> 如选 A，后续所有开发继续沿用 `npm run dev` 浏览器即开即测；发布时 `electron:build` 打包即可。无需重构任何业务代码。

## 二、后端 Java 架构升级评估

> 当前定版：JDK 25 + Spring Boot 4.1.1 + MyBatis Plus + Spring Security + JWT + MySQL 8 + Redis + 原生 WebSocket
> 本节回答：这个既定技术栈在 **1-3 年内是否需要以及怎样升级**。

### 2.1 后端核心层评估

| 层 | 当前 | 业界对照 | 一期判断 | 二期/远期升级路径 |
|----|------|---------|---------|------------------|
| **语言/运行时** | JDK 25 | 主流：Go / Java / Erlang | ✅ 不动；Java 在国内政企/信创天然优势 | — |
| **主框架** | Spring Boot 4.1.1 | Spring Boot 3.x 仍是主流 | ✅ 不动 | — |
| **ORM** | MyBatis Plus | 国内 Java 项目双雄(mybatis/jpa) | ✅ 不动 | — |
| **安全** | Spring Security + JWT | 业界主流 | ✅ 不动 | — |
| **缓存/状态** | Redis | 业界一致 | ✅ 不动 | — |
| **关系库** | MySQL 8 | 元数据存 MySQL 合理 | ✅ 不动 | — |
| **对象存储** | MinIO | S3 兼容标配 | ✅ 不动 | — |

### 2.2 WebSocket 接入层：Spring 原生 WS vs Netty 升级

**业界共识**：

| 方案 | 并发连接数 | 内存/连接 | 适用规模 | 主流实践 |
|------|-----------|----------|---------|---------|
| Spring 原生 WebSocket | 单机万级 | ~1-2KB/连接 | < 5000 并发 | 多数 Spring Boot 项目 |
| **Netty 接入层** | 单机 10 万+ | ~0.5KB/连接 | 万级+ | OpenIM / 钉钉后台 / 微信后台 |
| Go goroutine | 单机百万级 | ~8KB/连接 | 百万级 | Discord / WhatsApp |
| Erlang/OTP | 单机 100 万+ | 极低 | 大规模 | WhatsApp |

**本项目规模评估**：

| 规模 | 并发连接数 | 是否需要 Netty |
|------|-----------|---------------|
| **一期**（10-500 人企业） | ≤ 500 | ❌ **不需要** |
| **二期**（多企业 / 多租户） | 500-5000 | ❌ 仍可 Spring WS |
| **远期**（公有云 / 万人群） | > 5000 | ✅ 考虑 Netty 网关 |

**一期建议**：

> **继续用 Spring 原生 WebSocket（已完成 WsFrame 协议 + 心跳/重连/弱网队列/抖动重连）。** 不做 Netty 迁移。
>
> **唯一要做的事**：在接入层与业务层之间**预留 Netty 替换点**——业务服务调用 IWsGateway 接口，WsGateway 接口背后先用 Spring WebSocket 实现，后续一键替换为 Netty 实现，业务侧零改动。

### 2.3 消息总线：Redis Pub/Sub vs RocketMQ / Kafka

| 维度 | Redis Pub/Sub | RocketMQ | Kafka |
|------|--------------|----------|-------|
| 持久化 | ❌（瞬态） | ✅ | ✅ |
| 消息可靠性 | 丢消息（订阅方断线即丢） | 事务消息、可靠投递 | 高吞吐持久化 |
| 引入复杂度 | 低（已用 Redis） | 中（独立部署） | 中（独立部署） |
| 本项目一期需求 | ✅ 跨实例路由 + typing/presence | 全员广播削峰 | 消息流水持久化 |
| 竞品做法 | 瞬态事件走 Redis | 中大规模团队用 MQ | 庞大消息量 |

**一期决策**：

> **Redis Pub/Sub 起步。** 用于：
> ① 多实例部署时"消息投不到对方连接"的刚需路由
> ② typing / presence 瞬态事件分发
>
> **二期/远期**：若出现全员广播（> 500 人）或消息审计重放需求，引入 **RocketMQ**（国内政务/企业场景首选）。

### 2.4 消息存储：MySQL 流水 vs MongoDB vs Cassandra/ScyllaDB

**业界规模档位对照**：

| 日消息量 | 推荐存储 | 本项目预测 |
|---------|---------|-----------|
| < 10 万 | **MySQL + 分区表** | ✅ **一期落在此档** |
| 10 万 - 1000 万 | MongoDB / MySQL 分库分表 | 超出一期范围 |
| > 1000 万 | Cassandra / ScyllaDB | 超出一期范围 |

**一期决策**：

> **MySQL + 分区表**，不做任何 NoSQL 引入。
>
> **关键动作**（写库时即做）：
> 1. 消息表按 `conversation_id` 分区
> 2. 主键用**雪花 ID**（时间有序）
> 3. `(conversation_id, msg_id)` 联合覆盖索引
> 4. DAO 层**禁止泄漏 MySQL 方言**，接口抽象为 IMessageStore
>
> 这 4 件事**写入 `04-数据模型` 即完成**，不会增加代码量，但决定了未来能否平滑迁移到 Cassandra。

### 2.5 后端升级总图

```
当前(一期)                          二期                             三期
┌─────────────────────┐     ┌──────────────────┐     ┌──────────────────┐
│ JDK 25 + Boot 4.1.1 │     │      不变         │     │      不变         │
│ Spring WS (已有)     │ ──→ │      不变         │ ──→ │ Netty 接入层      │
│ Redis Pub/Sub       │     │ Redis Pub/Sub    │     │ RocketMQ         │
│ MySQL 8 分区表       │     │ MySQL 分库分表   │     │ Cassandra/ES     │
│ MinIO 对象存储       │     │      不变         │     │      不变         │
└─────────────────────┘     └──────────────────┘     └──────────────────┘
```

**一期结论：后端技术栈不需要"升级"，定版 = 终版（在一期范围内）。** 核心是**预留接口 + 做好分区设计**，为未来演进铺路。

## 四、私有化部署约束与信创路径

### 4.1 私有部署约束清单

| 约束 | 具体要求 | 涉及组件 |
|------|---------|---------|
| **无外网依赖** | 图标/字体/图片全部本地化，禁外部 CDN | 前端资源 |
| **无外部 API** | 短信/电话/地图瓦片/链接卡片等走 NoOp 适配器 | ASR / Geo / LinkPreview |
| **信创 Linux 兼容** | 麒麟 / Deepin / UOS + 鲲鹏 / 申威 CPU | Electron（内置 Chromium）|
| **离线安装** | Docker 镜像 + Nginx 一键部署，无需联网 | 全栈 |
| **数据合规** | 全量数据存客户本地 MySQL/MinIO，不留云 | 全栈 |
| **消息留痕** | 全量消息可审计、可回溯、不可加密（禁 E2EE）| 消息模块 |
| **录制永久保留** | 会议录制文件存 MinIO，由管理员手动清理 | LiveKit Egress |

### 4.2 国产化操作系统兼容性矩阵

| 系统 | 内核 | Electron 兼容 | WebSocket 兼容 | WebRTC 兼容 | RuoYi-IM 评估 |
|------|------|-------------|---------------|-------------|---------------|
| **统信 UOS** (桌面版) | Debian 系 | ✅ | ✅ | ✅ | ✅ 可运行 |
| **麒麟 Kylin** (桌面版) | Ubuntu/CentOS 系 | ✅ | ✅ | ✅ | ✅ 可运行 |
| **Deepin** | Debian 系 | ✅ | ✅ | ✅ | ✅ 可运行 |
| **麒麟信安** (服务器) | 自研内核 | ⚠️ 需实测 | ✅ | ⚠️ 需打 patch | ⚠️ 需验证 |
| **欧拉 openEuler** | CentOS 系 | ✅ | ✅ | ✅ | ✅ 可运行 |

> **结论**：走 Electron 路线，全信创桌面系统兼容。Tauri（依赖系统 WebView）在信创系统上风险更高。

### 4.3 外网依赖降级路径

| 外网依赖 | 降级策略 | 涉及接口 | 优先级 |
