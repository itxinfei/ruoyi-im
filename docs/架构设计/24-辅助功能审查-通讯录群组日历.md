### 1.3 发现的缺口（需要补充）

1. **CO-C-007 常用联系人**：需求要求「按联系频率自动排序」，但架构设计中无对应表/API/Store。建议方案：(a) 在im_user表中新增contact_freq_score BIGINT字段，每次发消息时+1更新；或 (b) 后端提供GET /im/contact/frequent接口，由SQL聚合im_session_member.join_time + 消息频次实时计算。

2. **CO-C-008 外部联系人**：需求明确「管理企业外联系人」，但整个架构（doc 04数据库设计、doc 06 API清单、doc 02 Store模块）完全没有im_external_contact表和相关API。当前仅ContactsPanel.vue UI层有Tab占位，前端无数据源、后端无接口。

3. **CO-C-010 好友状态变更WebSocket推送**：好友申请/通过/删除均无对应WS帧类型。当其他用户向当前用户发送好友申请时，接收方无法实时感知。建议定义EVENT类型下friend_request_notify与friend_change_notify帧。

4. **通讯录删除好友数据一致性**：DELETE /im/friend/{friendId}在doc 06中已定义，但无ws通知机制告知对方已解除关系，也未要求同步清理可能的im_friend_request残留数据。

### 1.4 不一致之处

1. **Tab命名不一致**：doc 09 §1.2 通讯录页面布局Tab为「组织架构 / 我的群组 / 常用联系人 / 外部联系人」四Tab；doc 13 §2.2 通讯录Tab为「组织架构 / 我的群组 / 我的好友 / 外部联系人」。**「常用联系人」vs「我的好友」语义不同，命名存在矛盾**。

2. **CO-C-010 好友管理vs API缺失**：im_friend_request表的to_user_id字段在doc 04中描述为「接收方用户ID」，但doc 06 API命名为PUT /im/friend/{requestId}/accept和reject，**缺少GET /im/friend/requests获取当前用户待处理好友申请列表的API**（doc 06仅定义了list列表，未列出requests请求列表端点）。

3. **搜索入口重复定义/Gateway路由缺失**：doc 08 §八 定义搜索入口为「会话栏顶部搜索框→全局搜索」+「聊天头部搜索按钮→会话内搜索」；doc 06 §13将搜索API定义在platform-search (8092)；但**doc 16 Gateway路由配置中未配置/im/search/\*\*路由**（仅配了/im/message/\*\*,/im/conversation/\*\*转向8081 im-message）。搜索请求打不到8092服务。

### 1.5 建议补充（文档:章节:内容）

1. **doc 04:2.8 im_user库**: 新增im_external_contact表（id, user_id, name, company, phone, email, remark, source, create_time, deleted）以支撑CO-C-008外部联系人。
2. **doc 06:§十 platform-user**: 新增GET /im/contact/frequent接口（CO-C-007常用联系人排序）、GET/POST/DELETE /im/external-contact/\*\*接口族（CO-C-008）、GET /im/friend/requests待处理列表。
3. **doc 05:§二 WS帧定义**: 在EVENT类型下新增friend_request_notify、friend_change_notify、friend_request_result三个action。
4. **doc 02:§3.3 im-contact.ts Store**: 新增externalContacts: ExternalContact[]状态与contactFrequencyMap状态。
5. **doc 16:§一路由规则**: 新增/im/search/\*\* → platform-search (8092)路由条目。
6. **doc 09 §一 通讯录**: 统一Tab命名——将「常用联系人」与「我的好友」合并为「好友管理」或拆分为两个独立Tab，明确各自语义。

### 2.3 发现的缺口（需要补充）

1. **CO-G-006 群公告编辑/删除**：doc 04 im_group_announcement表有完整字段设计，doc 06 API清单中仅有POST /im/group/{groupId}/announcement（发布公告）和GET（列表），**缺少编辑(PUT)和删除(DELETE)群公告的API端点**。

2. **CO-G-010 个人备注（群昵称）修改**：doc 04 DB中im_group_member.group_nickname字段已定义，但doc 06无修改群昵称的专用API。按照im-group服务API体系推测应由PUT /im/group/{groupId}/members/{userId}/nickname承载，但该端点在整篇doc 06中缺失。

3. **群成员变更WS notify**：当发生成员加入、移除、群主转让、群公告更新时，doc 05 WS帧表中无对应EVENT action（如group_member_change、group_announcement_update、group_transfer_result）。这些变更目前仅靠HTTP响应，无法实时同步到其他在线群成员。

4. **群解散/退出的离线用户处理**：当群主解散群时，离线成员无法收到WS帧，重新上线后如何感知群已解散？doc 04/05无im_offline_group_event机制。

5. **im_group.description字段更新路径不清晰**：doc 04中description VARCHAR(500) NULL，需求CO-G-002要求展示「群描述」，API GET中会返回，但无独立update API修改描述（PUT /im/group/{groupId}可通用更新）。

### 2.4 不一致之处

1. **CO-G-003 移除成员API与DB唯一键对齐**：doc 06 §四 定义DELETE /im/group/{groupId}/members/{userId}（含路径参数userId），与DB im_group_member的唯一键(group_id, user_id)对齐。但doc 06 §四 im-group PUT /im/group/{groupId}更新群信息时，**可更新字段未明确白名单**。

2. **CO-G-006 群公告 与 IM-G-003 群公告命名混淆**：doc 08 IM核心需求中IM-G-003定义为「群公告：发布/编辑/删除群公告」，doc 09 CO-G-006同样定义为「发布、编辑、删除群公告」。**IM-G-003与CO-G-006实质描述同一功能**，但分属不同模块文档，功能完全重叠，建议统一引用。

3. **CO-G-009 群文件与CO-F-001~006重复归属**：im_group_file表同时被CO-G-009（群文件面板）和CO-F-001（群文件列表）引用，且im-file-storage服务中GET /im/group/{groupId}/files端点共享。**群文件需求在CO-G与CO-F两处重复描述**，建议文档间建立交叉引用。

### 2.5 建议补充（文档:章节:内容）

1. **doc 06:§四 im-group**: 新增PUT /im/group/{groupId}/announcement/{announcementId}（编辑公告）、DELETE /im/group/{groupId}/announcement/{id}（删除公告）、PUT /im/group/{groupId}/members/{userId}/nickname（修改群昵称）。
2. **doc 05:§二 WS帧定义**: 在EVENT类型下新增group_member_change、group_announcement_update、group_owner_transfer、group_dismiss四个action。
3. **doc 06:§四**: 明确PUT /im/group/{groupId}的RequestBody字段白名单（允许更新：group_name, description, avatar, max_members, join_type, status）。
4. **doc 09 §二 CO-G**: 在CO-G-006与CO-G-009处交叉引用IM-G-003与CO-F，统一归属。

### 3.3 发现的缺口（需要补充）

1. **PL-CA-005 日程提醒推送链路不完整**：doc 04 DB中有im_event_reminder表（含is_sent状态位），doc 08中有定时任务相关概念（RabbitMQ延迟队列），但：
   - **doc 05 WS帧表无calendar_reminder action**——后端定时任务扫描到提醒时间后，通过什么通道推送到客户端未定义。
   - 桌面通知走Electron Notification API（doc 02 §6.2已设计useElectron().showNotification），但**站内提醒（站内红点/Badge）Badge数量更新无对应入口**。
   - **建议**：新增EVENT类型下calendar_reminder action，后端扫描后通过WS推送给参与者；站内提醒可通过useElectron或Badge API。

2. **PL-CA-006 共享日历（空忙状态）完整缺失**：需求要求「查看同事的空忙状态」，架构中：
   - DB无im_calendar_permission或im_calendar_share表。
   - API无GET /im/calendar/availability端点。
   - 无权限模型定义（默认是否公开？是否仅好友可见？是否需要审批？）。
   - **这是一个完整功能模块缺失**，需在DB、API、WS、Store四层补充。

3. **日历模块缺少Vuex Store**：doc 02 §3 Vuex Store定义了im-session、im-message、im-contact、im-call四个命名空间模块，**无calendar.ts**。虽然日历数据可通过API缓存，但日历视图状态（当前选中日期、当前视图模式、日程缓存Map）应有Store管理。

4. **日历事件重复规则RRULE解析未设计**：doc 04 im_schedule_event有repeat_rule VARCHAR(200) COMMENT 'RRULE' 字段，但服务层解析逻辑（生成重复事件实例、计算下次触发时间）、以及是否依赖第三方库（如RFC 5545 RRULE解析器）完全未定义。

5. **事件参与者邀请响应WS通知缺失**：参与者收到日历邀请后，组织者无法实时感知接受/拒绝状态变化。doc 05 WS帧无calendar_invite_response action。

### 3.4 不一致之处

1. **PL-CA-008 日程颜色类型与event_type枚举不完全对齐**：doc 04 DB定义event_type TINYINT COMMENT '0=会议 1=个人 2=提醒 3=任务'（共4种），而doc 09/需求PL-CA-008颜色描述为「工作/会议/个人/提醒」（共4种，但命名不同）。**DB中为「会议/个人/提醒/任务」，需求中为「工作/会议/个人/提醒」**——「任务」vs「工作」存在含义混淆。doc 13 Design Token定义了--dt-event-work/meeting/personal/reminder四种颜色token，与需求一致但与DB不一致（DB缺work token对应、多了「任务」类型）。

2. **日历服务边界与站内Badge联动不明确**：doc 09 §10.2联动规则中「日历日程到点→推送桌面通知+站内红点」，站内红点的Badge计数是否与im-real-time服务关联，还是由collab-calendar自行计算？doc 08无此说明。

3. **im_event_reminder提醒类型字段remind_type与实际需求**：doc 04定义为'0=通知 1=邮件'，但doc 09需求PL-CA-005写的是「桌面通知+站内」——「邮件」提醒类型理论上属于MailProvider供应商服务（doc 02），但日历模块本身无MailProvider注入设计。**日历模块与MailProvider的集成未定义**。

### 3.5 建议补充（文档:章节:内容）

1. **doc 04:2.5 im_calendar库**: 新增im_calendar_permission表（id, user_id, viewer_id, permission_level, expiry_time, created_time）以支撑PL-CA-006共享日历权限模型。
2. **doc 06:§七 collab-calendar**: 新增GET /im/calendar/availability接口（查询指定用户/日期范围内的空忙状态）、POST /im/calendar/{eventId}/cancel（取消日程，与删除语义不同——取消应通知所有参与者）。

### 最高优先级修复项（P0）

1. **PL-CA-005/006 日历提醒推送链路**：涉及DB→服务→WS→UI全链路，若不在架构层面定义清楚，后期将需要大规模重构。
2. **WS实时通知帧统一补充**：三个模块共缺失约10个EVENT action，直接影响用户体验（好友申请无实时通知、群成员变动无推送、日历邀请响应不实时）。
3. **Gateway平台搜索路由**：/im/search/** 在Gateway中缺失配置（doc 16未配置），搜索功能上线后将出现404。
