> **定位**：对 CO-D（DING 消息）、CO-F（群文件）、CO-S（消息收藏）三大辅助功能模块进行需求文档与架构设计文档的深度覆盖度与一致性审查。
> **审查日期**：2026-10-30
> **审查范围**：需求文档 07/08/09 + 架构设计 02/03/04/05/06/08/20

## CO-D DING 消息 审查

### 1. 需求清单

| 编号 | 需求 | 说明 | 状态 |
|------|------|------|------|
| CO-D-001 | 发送 DING | 选择接收人（可多人）→ 填写内容 → 选择提醒方式 → 发送 | ✅ |
| CO-D-002 | DING 确认 | 接收方点击确认回执 | ✅ |
| CO-D-003 | DING 统计 | 发送方查看确认进度（已送达/已确认/未确认） | ✅ |
| CO-D-004 | DING 历史 | Tab: [收到的 DING] [我发送的 DING] | ✅ |
| CO-D-005 | DING 限制 | 每人每天最多发送 10 条 DING | ✅ (C-010) |

### 2. 架构覆盖矩阵

| 需求维度 | WS 协议 (05/25) | REST API (06/24) | 数据库 (04) | 前端组件 (02) | 中间件/限流 (08) |
|----------|----------------|-------------------|-------------|---------------|-------------------|
| CO-D-001 发送 | ⚠️ 见不一致 | ❌ 06 未定义；24 有 11 端点 | ⚠️ 仅靠 msg_type=DING | ❌ 无 im-ding Store 模块 | ❌ 无日限额实现 |
| CO-D-002 确认 | ⚠️ 未定义确认帧 | ❌ 06 未定义；24 有 confirm | ❌ 无回执表 | ❌ 无确认 UI 设计 | — |
| CO-D-003 统计 | ⚠️ 未定义统计帧 | ❌ 06 未定义；24 有 receipts | ❌ 无统计视图 | ❌ 无统计面板 | — |
| CO-D-004 历史 | — | ❌ 06 未定义；24 有 received/sent | ⚠️ 从 im_message 查 | ❌ 未设计历史面板 | — |
| CO-D-005 限额 | — | ❌ 无限额校验接口描述 | — | — | ❌ 无 Redis 限流 key |

### 3. 缺口（Gap）

| # | 缺口 | 严重度 | 说明 |
|---|------|--------|------|
| G1 | **无独立 DING 数据库表** | 🔴 高 | DING 仅作为 im_message.msg_type=DING 存储，缺少 im_ding（DING 主表）和 im_ding_receipt（确认回执表），无法独立追踪回执状态与统计 |
| G2 | **无 DING 日限额实现** | 🔴 高 | C-010 规定每人每天 10 条，但 08 Redis 模型中无 im:ding:limit:{userId}:{date} key，06 API 无校验错误码 |
| G3 | **DING 状态机缺失** | 🟡 中 | DING 有独立生命周期（已发送→已送达→已确认），但无状态机定义 |
| G4 | **前端无 DING Store 模块** | 🟡 中 | 02 有 EVENTS.DING_RECEIVED 事件常量，但 Store 章节无 im-ding.ts |
| G5 | **DING 发送 WS 帧类型冲突** | 🟡 中 | 05 定义为 EVENT/ding，25 定义为 NOTIFY/NOTIFY_DING |
| G6 | **回执批量上报机制缺失** | 🟡 中 | 参照 AR-11，但无 DING 专用批量回执设计 |
| G7 | **06 REST API 完全缺失 DING** | 🟡 中 | 06 无 DING 端点，仅 24 有 11 端点清单 |

### 4. 不一致（Inconsistency）

| # | 文档 A | 文档 B | 冲突描述 |
|---|--------|--------|----------|
| I1 | 05-WS协议 §2.2 | 25-WS消息类型 §1.2 | DING 帧：EVENT/level 字段 vs NOTIFY/priority 字段，数据结构不同 |
| I2 | 04-数据库设计 §2.1 | 需求 09 §4 | DING 仅作为消息类型存储，但需求要求确认/统计/限额等独立能力 |
| I3 | 06-RESTful API | 24-API端点清单 | 06 无 DING 端点，24 列出 ImDingMessageController 11 端点 |
| I4 | 09 §4.2 | 09 §10 微交互 | DING 提醒方式仅保留应用内，但 NotifyProvider 适配器未明确 |

### 5. 建议

1. **【P0】** 新增 im_ding 表 + im_ding_receipt 表，独立于 im_message
2. **【P0】** 08 Redis 增加 im:ding:limit:{userId}:{yyyyMMdd} 计数 key（TTL=24h），错误码 10007
3. **【P1】** 统一 WS 通知帧：DING 使用 NOTIFY/NOTIFY_DING（schema 更完整），05 同步更新
4. **【P1】** 前端 02 Store 新增 im-ding.ts 模块
5. **【P2】** 06 REST API 补全 DING 章节，与 24 的 11 端点对齐

## 审查总结

| 模块 | 需求覆盖率 | 架构完整度 | 文档一致性 | 综合评级 |
|------|-----------|-----------|-----------|----------|
| CO-D DING 消息 | 5/5 (100%) | 2/5 (40%) | ⚠️ 高冲突 | 🟡 需优先补全 |
| CO-F 群文件 | 6/6 (100%) | 2/6 (33%) | ⚠️ 中冲突 | 🟡 需优先补全 |
| CO-S 消息收藏 | 6/6 (100%) | 4/6 (67%) | ⚠️ 编号冲突 | 🟡 需统一编号 |

> **核心结论**：三个模块需求定义完整（3/3 通过），但架构实现度普遍偏低（平均 45%），且均存在跨文档的不一致问题。建议优先解决数据库表缺失（P0）、REST API 补全（P0）与需求编号统一（P1），再推进前端 Store 与组件落地。
