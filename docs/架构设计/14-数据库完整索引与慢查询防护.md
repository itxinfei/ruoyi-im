## 一、索引设计原则 (红线)

| 原则 | 说明 |
|------|------|
| **索引命名** | `idx_{表名}_{字段名}` / `uk_{表名}_{字段名}` (唯一) |
| **单表索引数** | ≤ 5 个 (>= 6 个需技术负责人审批) |
| **联合索引** | 遵循"最左前缀"原则, 高区分度字段靠左 |
| **覆盖索引** | 高频查询尽可能使用覆盖索引, 避免回表 |
| **禁止索引** | 低区分度字段 (性别/状态若只有 2-3 种值, 单独索引可能不如全表扫描) |
| **验证要求** | 新增 SQL 必须 EXPLAIN 验证执行计划 |

### 1.1 EXPLAIN 判断标准

```
可以接受的执行计划:
✅ type = const / eq_ref / ref / range
✅ Extra = Using index   (覆盖索引最优)
✅ Extra = Using index condition (ICP 下推优化)

必须优化的执行计划:
❌ type = ALL           (全表扫描)
❌ type = index         (全索引扫描, 仍需排序)
❌ Extra = Using filesort (文件排序)
❌ Extra = Using temporary (临时表)
❌ rows > 10000         (预估扫描行过多)
```

#### im_message 表索引

| 索引名 | 字段 | 类型 | 用途 |
|--------|------|------|------|
| `idx_msg_session_id` | `session_id` + `server_seq` DESC | 联合 B+Tree | 按会话查历史消息 |
| `idx_msg_sender_time` | `sender_id` + `send_time` DESC | 联合 B+Tree | 某人发的消息列表 |

| `idx_msg_status` | `status` | 普通 B+Tree | 待确认消息查询 (低区分区, 慎用) |

```sql
-- 创建索引
ALTER TABLE im_message ADD INDEX idx_msg_session_id (session_id, server_seq DESC);
ALTER TABLE im_message ADD INDEX idx_msg_sender_time (sender_id, send_time DESC);
ALTER TABLE im_message ADD INDEX idx_msg_session_time (session_id, send_time DESC);

-- 验证 EXPLAIN
EXPLAIN SELECT * FROM im_message
WHERE session_id = '1780000000001'
ORDER BY server_seq DESC
LIMIT 20;
-- ✅ 期望: type=ref, key=idx_msg_session_id, Extra=Using index condition
```

## 三、SQL 慢查询防护机制

### 3.1 MyBatis Plus 拦截: 分页禁 OFFSET

```java
@Configuration
public class MybatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();

        // 分页插件: 禁 OFFSET, 用游标
        PaginationInnerInterceptor page = new PaginationInnerInterceptor();
        page.setOverflow(true);           // 页数溢出返回空
        page.setMaxLimit(100L);           // 单次最多 100 条
        interceptor.addInnerInterceptor(page);

        // 防全表更新/删除
        BlockAttackInterceptor block = new BlockAttackInterceptor();
        interceptor.addInnerInterceptor(block);

        return interceptor;
    }
}
```

### 3.2 Druid 防火墙 + 慢 SQL 监控

```yaml
# application.yml
spring:
  datasource:
    druid:
      filter:
        wall:
          enabled: true
          db-type: mysql
          # 禁止 DROP TABLE / TRUNCATE
          config:
            drop-table-allow: false
            truncate-allow: false
            # 禁止多语句
            multi-statement-allow: false
            # 禁止无 WHERE 的 UPDATE/DELETE
            update-where-always-true-check: true
            delete-where-always-true-check: true
        stat:
          enabled: true
          slow-sql-millis: 500       # 500ms 算慢 SQL
          log-slow-sql: true
          merge-sql: true
```

### 3.3 慢 SQL 告警规则 (已有 + 新增)

```yaml
# prometheus/alerts.yml 补充
- alert: SlowSQLQuery
  expr: rate(mysql_global_status_slow_queries[5m]) > 10
  for: 3m
  labels:
    severity: warning
  annotations:
    summary: "慢查询速率 > 10/min"

- alert: LongRunningQuery

```

## 四、分库分表策略

> **一期**: 9 库 37 表, 不拆分。按单库扛 500w 行 / 500 人规模, 够用 2-3 年。
> **二期** (5000+ 人以上) 才考虑:

| 表 | 拆分方式 | 拆分键 | 时机 |
|----|---------|--------|------|
| im_message |按月分表 + 按 session_id 分库 | session_id 取模 | 单表超 500w 行 |
| im_msg_offline | 7 天过期 | create_time | 无需分表, TTL 清理 |
| im_file | 按 uploader_id 分库 | 上传者 | 单库文件数超 1000w |
| im_audit_log | 按月分表 | operation_time | 单表超 1000w 行 |

### 4.1 分表命名规则

```
im_message_202501       -- 按月
im_message_202502
im_audit_log_202501
im_audit_log_202502
```

### 4.2 ShardingSphere 配置 (二期预留)

```yaml
# 二期启用, 一期保持 9 库不分表
spring:
  shardingsphere:
    datasource:
      names: ds0,ds1,ds2
    sharding:
      tables:
        im_message:
          actual-data-nodes: ds${0..2}.im_message_${202501..202512}
          table-strategy:
            standard:
              sharding-column: session_id
              sharding-algorithm-name: hash_mod
          key-generator:
            column: id
            type: SNOWFLAKE
```

## 五、表状态监控 (已有 + 新增)

```sql
-- 月度巡检 SQL
-- 1. 检测大表 (行数 > 100MB)
SELECT TABLE_NAME, TABLE_ROWS, ROUND(DATA_LENGTH/1024/1024,2) AS size_mb
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'im_msg'
  AND (DATA_LENGTH > 100*1024*1024 OR TABLE_ROWS > 10000000)
ORDER BY DATA_LENGTH DESC;

-- 2. 检查索引使用率
SELECT TABLE_NAME, INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAME
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = 'im_msg'
ORDER BY TABLE_NAME, INDEX_NAME;

-- 3. 查找未用索引
SELECT object_schema, object_name, index_name
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE index_name IS NOT NULL
  AND count_star = 0
  AND object_schema = 'im_msg';
```
