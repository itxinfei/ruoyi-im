#### 3.3.3 状态机图审查结果

**架构中是否存在完整状态机图？** —— ❌ **不存在**

doc 09（需求）与 doc 04（DB）均未提供完整审批状态流转图。缺失内容包括：

1. **状态转换触发条件未定义**：
   - 谁可以将 1(待审批) → 2(审批中)？是提交即转还是首节点审批人接单才转？
   - 谁可以将任意非终态 → 5(已撤回)？仅发起者本人？有无时间窗口？
   - 转交(PUT /im/approval/{id}/transfer)后原节点如何处理？

2. **缺失状态**：
   - "转交"作为 action=3 存在于 `im_approval_node`，但不是 `im_approval` 的 status —— 这是否意味着转交后 status 仍为 2(审批中)？
   - 需求文档(09)描述的状态未包含"审批中"，但 DB 状态 2 正好是"审批中"。两者不一致。

3. **缺少 Mermaid 状态机图**：对比 doc 05 通话信令有 `IDLE → CALLING → CONNECTED → ENDED` 完整状态机，审批流程作为核心业务状态机更应有可视化定义。

### 3.4 im_approval_node 多级审批能力审查

#### 表结构（doc 04 §2.4）

```sql
CREATE TABLE im_approval_node (
    id              BIGINT      NOT NULL,
    approval_id     BIGINT      NOT NULL,
    node_name       VARCHAR(64) NOT NULL,
    approver_id     BIGINT      NOT NULL,
    action          TINYINT     NULL COMMENT '1=通过 2=驳回 3=转交',
    comment         VARCHAR(500) NULL,
    operate_time    DATETIME    NULL,
    create_time     DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    KEY idx_approval (approval_id, id),
    KEY idx_approver (approver_id, action)
);
```

#### 多级审批支持度评估

| 能力 | 支持度 | 说明 |
|------|:------:|------|
| 串行审批（A→B→C逐级） | ⚠️ 部分 | 依赖 `id` 自增决定顺序，无显式 `node_order` 字段 |
| 并行审批（多人同时审批） | ❌ 不支持 | 无 `node_group` 字段区分审批分支 |
| 会签（全部通过才过） | ❌ 不支持 | 无 `approve_mode` 字段（ANY/ALL） |
| 或签（任一通过即过） | ❌ 不支持 | 同上 |
| 转交 | ⚠️ 部分 | action=3 存在，但无转交原因字段、无转交后新审批人记录 |
| 加签 | ❌ 不支持 | doc 13 UI 定义为底部操作按钮，但 DB/API 无支撑 |
| 驳回后返回修改 | ❌ 不支持 | 无"驳回→修改→重新提交"的状态回流定义 |
| 审批人委托/代理 | ❌ 不支持 | 无 `delegate_approver_id` 字段 |
| 超时自动处理 | ❌ 不支持 | 无 `timeout_hours`、`auto_action` 字段 |

#### 结论

`im_approval_node` 当前仅是**扁平的审批节点记录表**，不支持复杂的多级审批场景。需扩展字段（`node_order`, `approve_mode`, `node_type`, `delegate_approver_id`, `timeout_hours`）才能满足企业级审批需求。
