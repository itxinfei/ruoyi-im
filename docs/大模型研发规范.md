本文档是 AI 开发行为的**最高优先级约束来源**，覆盖从前端到后端、从命名到架构的全部研发活动。

- 与 `CLAUDE.md`（全局入口）、`.agent/rules/`（前端/后端专项规则）、`.claude/rules/`（UI 生成 Prompt 规范）配合使用
- 所有 AI 执行开发任务前，**必须先读取并遵守**本文档的所有约束
- 任何冲突以本文档为准；本文档未覆盖的内容按 `CLAUDE.md` 补充规则执行

## 3. AI 开发 7 大原则

### 3.1 零占位原则

**禁止生成：**
- "开发中" / "即将上线" 等占位提示页面
- 含 `// TODO` / `// FIXME` 的注释
- 返回静态假数据的方法（除非明确标注为"临时接口供联调用"并在 48 小时内替换）
- 空壳组件（只有 template 骨架无逻辑实现）
- Store 中未实现的 action（仅有函数签名无函数体）
- 永远返回 `true` / `null` 的异常处理 catch 块

**必须生成：**
- 完整可运行的代码
- 所有分支的异常处理（try-catch、空值判断、边界条件）
- 真实的数据流（API / WebSocket / Store 端到端联动）
- 编辑/删除等写操作的确认弹窗

### 3.2 完整链路原则

AI 生成的任何功能必须包含**完整链路**：

```text
ViewModel (Vue) → Composable → API 调用 → DTO/参数 → 后端 Controller → Service → Mapper → DB
```

- 禁止只写一半（如只做前端不做后端，或只做 backend 不做 frontend）
- 如需分段交付，必须明确标注：
  - **临时方案**内容是什么
  - **完整方案**路径是什么
  - **转换时机**是什么条件触发
- WebSocket 功能必须同时实现：前端监听 + 后端推送 + 心跳机制 + 重连策略

### 3.3 命名锁定原则

| 层级 | 规范 | 示例 |
|------|------|------|
| 数据库表名 | `im_xxx`（蛇形） | `im_message`, `im_user` |
| 数据库字段 | `xxx_yyy`（蛇形） | `sender_id`, `created_at` |
| Java 类 | `XxxService` / `XxxController` / `XxxDTO`（大驼峰） | `MessageService` |
| Java 方法/变量 | `xxxYyy`（小驼峰） | `findById`, `userId` |
| Vue 组件 | `XxxPanel.vue` / `XxxDialog.vue`（PascalCase） | `ChatWindow.vue` |
| Vuex 模块 | `im-xxx.ts`（kebab-case, `im-` 前缀） | `im-message.ts` |
| API 文件 | `xxxApi.ts`（camelCase + `Api` 后缀） | `messageApi.ts` |
| 常量 | `XXX_YYY`（大写下划线） | `MAX_RETRY_COUNT` |
| 枚举 | `XxxStatusEnum` / `XxxTypeEnum`（PascalCase + 后缀） | `MessageStatusEnum` |
| 路由 | `/im/xxx/yyy`（kebab-case URL） | `/im/message/list` |
| Redis Key | `im:{module}:{bizId}`（冒号分隔） | `im:message:1001` |
| WS Action | `verb_object`（snake_case） | `message_send`, `user_typing` |
| CSS 类名 | `block__element--modifier`（BEM） | `chat-window__header--active` |

### 3.4 Token-First 视觉原则

AI 修改/生成样式时的**强制流程**：

1. **先查** `design-tokens.scss` 是否存在可复用 token
2. **无合适 token** 时，必须先在 `design-tokens.scss` 中新增并在本文档"第 8 章"记录
3. **禁止**凭经验写 `color: #1890ff` 等硬编码色值
4. **禁止**在组件 `<style>` 块中引入新的颜色变量（必须走 Design Token）
5. **暗色模式**：每个新增 token 必须同时定义亮色和暗色两个变量

**8pt 栅格合规检查：**
- 间距：4px / 8px / 12px / 16px / 24px / 32px（禁止使用 5、7、9、10 等非 8pt 倍数）
- 字号：12px / 13px / 14px / 16px / 18px / 20px（禁止 11、15、17 等）
- 圆角：`var(--dt-radius-sm)`=4px, `var(--dt-radius-md)`=8px, `var(--dt-radius-lg)`=12px
- 禁止使用 `!important`（第三方 UI 库覆盖除外）

### 3.5 DDD 分层不可越权原则

**后端 Java 代码调用方向（严格单向）：**

```text
Controller → Service → Mapper / Repository
               ↓
         Domain Service（协调跨聚合根）
```

**禁止行为：**
- Controller 直接调用 Mapper（绕过 Service）
- Service 之间互相循环依赖（使用 Domain Service 解耦）
- 工具类 / 静态方法调用 Service（除非是纯数据计算工具）
- 数据库 Entity 暴露在 Controller 层（必须转为 DTO / VO 返回）
- Service 层出现 SQL 片段（SQL 属于 Mapper 层职责）
- Repository 直接被 Controller 调用

**事务管理规范：**
- 跨 Service 事务必须使用 `@Transactional` 或 Saga 模式
- 事务范围控制在 200ms 以内（禁止大事务持有锁）
- 必须在事务提交后才发送 MQ / 事件消息

### 3.6 状态机合法流转原则

AI 在实现任何状态管理时必须：

1. **状态流转图**：在代码注释中画出完整状态流转图（含非法流转标注）
2. **Mutation/Action 统一入口**：状态变更必须通过 Mutation（Vuex）或 Action（业务），禁止直接修改 state
3. **异常兜底**：每个状态必须有对应的兜底处理（网络失败、超时、并发冲突）
4. **WebSocket 竞态**：WebSocket 推送的状态变更必须考虑时序竞态（使用版本号 / 时间戳校验）

**示例注释模板：**
```java
/**
 * 消息状态流转:
 *   DRAFT --send--> SENDING --ack--> SENT --read--> READ
 *   SENDING --timeout/fail--> FAILED --retry--> SENDING
 *   FAILED --max_retry--> DEAD_LETTER
 */
```

### 3.7 数据一致性原则

- 写操作完成后必须返回最新状态（乐观返回 + 异步确认）
- 关键业务使用 `@Version` 实现乐观锁（库存、计数、余额）
- 缓存与 DB 一致性：更新 DB 后必须失效对应缓存（非延迟双删场景）
- 事务消息：跨服务数据一致性优先使用本地消息表模式

## 4. 反模式清单

### 前端反模式（禁止出现）

| 序号 | 反模式 | 正确做法 |
|------|--------|----------|
| F01 | 直接使用 `document.querySelector` | 使用 `ref` 或 `getCurrentInstance` |
| F02 | 使用 `localStorage` 做状态管理 | 使用 Vuex Store（禁止 Pinia） |
| F03 | `watch` 深层对象不指定 `deep: true` | 明确声明 watch 选项 |
| F04 | template 中写复杂三元/逻辑表达式 | 使用 `computed` 提取 |
| F05 | 单个组件超过 300 行不拆分 | 拆分子组件 / Composable |
| F06 | 大列表不使用 `v-for` + `:key` 优化 | 使用虚拟滚动 / `v-memo` |
| F07 | props 传递超过 3 层 | 使用 `provide/inject` 或重构 |
| F08 | 使用 `$parent` / `$children` 跨级访问 | 使用事件 emit / 全局状态 |
| F09 | 在 `computed` 中产生副作用（赋值/API） | 副作用放入 `methods` / `watch` |
| F10 | 使用 `setTimeout` 处理异步流程 | 使用 `async/await` / `Promise` |
| F11 | 暗色模式使用 CSS filter 反转颜色 | 使用 CSS 变量切换主题 |
| F12 | 使用 `@import` 引入全局样式（导致顺序混乱） | 使用 `<style scoped>` 或 CSS Module |
| F13 | 在 `beforeDestroy` 中不清理定时器 / 事件 | 必须清理 `setInterval` 和自定义事件 |
| F14 | v-if 和 v-for 用在同一元素上 | 使用 `v-for` + template 包裹 v-if |
| F15 | 使用 `JSON.parse(JSON.stringify())` 做深拷贝 | 使用 `structuredClone` 或工具函数 |

### 后端反模式（禁止出现）

| 序号 | 反模式 | 正确做法 |
|------|--------|----------|
| B01 | 跨 Service 事务不用 `@Transactional` | 使用 Transactional 或 Saga 模式 |
| B02 | 库存/计数场景不使用 `@Version` 乐观锁 | 乐观锁 + 重试机制 |
| B03 | MyBatis 全表扫描（未命中索引） | 先 `EXPLAIN` 确认索引命中 |
| B04 | 大事务持有锁超过 200ms | 拆分事务，异步化非关键逻辑 |
| B05 | N+1 查询（循环中逐条查关联数据） | 使用 `JOIN FETCH` 或批量查询预加载 |
| B06 | 明文存储密码 / token | 使用 bcrypt / Argon2 加密存储 |
| B07 | Controller 直接返回 Entity | 使用 DTO / VO 封装响应 |
| B08 | 在循环中调用数据库查询 | 批量查询后内存分组 |
| B09 | 忽略 Optional 可能为空 | 显式处理 `Optional.orElse/orElseThrow` |
| B10 | 使用 `+` 号拼接 SQL 字符串 | 使用 `#{}` 参数绑定防注入 |
| B11 | `synchronized` 锁住业务方法 | 使用分布式锁（Redis Redisson） |
| B12 | 日志打印完整 request/response | 脱敏后打印关键字段 |
| B13 | 异常直接 `printStackTrace()` | 使用 SLF4J + 统一异常处理 |
| B14 | `@Transactional` 捕获了异常却不抛出 | 事务方法内不允许静默吞异常 |
| B15 | `@Autowired` 字段注入（无法单测） | 使用构造器注入 |

## 5. 代码验收标准（DoD）

AI 每次提交的代码**必须**通过以下检查清单：

### 功能完整性

- [ ] 主流程端到端畅通（前端 → API → 后端 → DB → 前端展示）
- [ ] 异常分支有处理（网络失败、超时、空值、权限不足）
- [ ] 空状态 UI 完整（列表为空、搜索无结果）
- [ ] 加载态 UI 完整（Skeleton / Loading Spinner）
- [ ] 错误态 UI 完整（友好提示 + 重试按钮）
- [ ] 编辑/删除操作有确认弹窗
- [ ] WebSocket 消息有心跳 + 断线重连

### 视觉合规性

- [ ] 100% 调用 Design Token（零硬编码 hex 颜色）
- [ ] 无 `!important`（第三方覆盖除外）
- [ ] 无 `animation` / `filter` / `backdrop-filter`（登录页品牌渐变除外）
- [ ] 圆角 / 字号 / 间距符合 8pt 栅格系统
- [ ] 暗色模式下颜色变量已定义并生效

### 架构合规性

- [ ] DDD 分层正确（无反向依赖）
- [ ] 命名严格符合第 3.3 节规范
- [ ] REST API 前缀统一为 `/im/`
- [ ] 返回类型统一为 `Result<T>`
- [ ] WS action 已在 `docs/05-WebSocket 协议速查表.md` 中定义

### 测试合规性

- [ ] 关键 Service 方法有单元测试（JUnit 5 + Mockito）
- [ ] 测试可独立运行（不依赖外部服务）
- [ ] 测试覆盖率 > 80%（新增代码部分）

## 6. 协作协议

AI 与人类开发者协作时必须遵守：

### 输出规范

| 场景 | 要求 |
|------|------|
| 修改 ≤3 个文件 | 回复顶部列出变更文件清单 + 一句话摘要 |
| 修改 >5 个文件 | 输出影响范围评估（涉及模块、潜在风险点） |
| 不确定需求 | 明确列出假设条件，请求人类确认后再实现 |
| 发现规范冲突 | 标注 `[规范冲突]` 并给出解决建议 |
| 临时方案 | 标注 `[TEMP]` 并注明替换时间和完整方案路径 |

### 修改声明模板

每次代码变更时在回复顶部输出：

```text
## 变更清单
- 文件1: 变更类型（新增/修改/删除）— 一句话说明
- 文件2: 变更类型 — 一句话说明

## 影响范围
- 涉及模块: xxx
- 潜在风险: xxx（无风险则写"无"）

## 假设条件
- （无假设则写"无"）
```

## 7. 质量红线

以下指标**任一不达标**，视为 AI 任务失败，必须修复后重新提交：

| 指标 | 红线阈值 | 处理方式 |
|------|----------|----------|
| TypeScript `any` 出现次数 | > 5 个 / 文件 | 使用具体类型或 `unknown` 替代 |
| 硬编码 hex 颜色 | > 0 次 | 替换为 Design Token 变量 |
| `TODO` / `FIXME` / `HACK` 注释 | > 0 个 | 实现完整逻辑或上报人类处理 |
| `!important` 出现次数 | > 0 次 | 提升选择器优先级（第三方覆盖除外） |
| 单文件行数 | > 400 行 | 提示人类 / 自动拆分子组件或工具函数 |
| 单方法行数 | > 50 行 | 提示人类 / 自动拆分子方法 |
| 异常 catch 块为空 | > 0 个 | 补全错误处理逻辑 |
| 未使用的 import | > 0 个 | 清理 |

## 8. 文档维护

### 版本管理

- 规范版本号格式：`vX.Y`
  - `X` = 大版本（架构级变更、重大原则调整）
  - `Y` = 小更新（新增条款、补充反模式、Token 新增记录）
- 每次更新需在本文档顶部 `生效日期` 字段同步更新

### 同步机制

- `CLAUDE.md` 中记录的每次"修复记录"必须在本文档的对应章节同步
- 新增 Design Token 必须在第 3.4 节流程执行后记录于此
- 新增反模式必须在第 4 节补充

### Token 新增记录（模板）

当新增 Design Token 时，按以下格式追加记录：

```markdown
#### v1.1 新增 Token: --dt-xxx-yyy
- **用途**: 描述该 token 使用的 UI 场景
- **亮色值**: #xxxxxx
- **暗色值**: #xxxxxx
- **使用文件**: 列出首次使用该 token 的组件
- **审批人**: 人类开发者确认
```
